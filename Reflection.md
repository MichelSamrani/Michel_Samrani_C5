# Reflection

I drew the line between tools by asking two questions about each one: does it change anything, and can I describe it without using "and"? Looking up a forecast changes nothing, so `get_weather_forecast` is the Data tool. It only reads from Open-Meteo, and the tests check that it never writes the trips file. Saving a plan is the only side effect in the system, so `save_trip_plan` is the Action tool. It takes the date as an explicit argument and knows nothing about weather. The tricky part was the forecast tool, which has to turn a city name into coordinates before it can ask for weather. I kept geocoding inside it as an internal step instead of making it a fourth tool. The model never needs coordinates on their own, and a separate geocoding tool would only add a round trip. The decision logic ("which day is best?") was the part that would have broken single-purpose design if I had put it in either of the other tools. That made it the natural content of `plan_outdoor_trip`, the Orchestration tool. It calls the same core functions as the other two tools in sequence: forecast, rank, then save. It also has a predictable "nothing saved" outcome when every day is too rainy. To keep failures predictable, every bad input or outage raises a `ToolError` with a readable message: unknown city, days out of range, a malformed or past date, a duplicate trip, or an unreachable weather service. Because of this, the agent can explain the problem to the user instead of failing silently.

Three tools felt right for this use case. They map cleanly onto the "ask, act, delegate" requests a user would make, and the agent rarely confused them because each description starts with its category and states when to use it. The main cost of the orchestration tool is that its ranking policy (rain under 60%, about 22 °C, low wind) is hard-coded, so the model can't adjust it for activities like skiing. Next steps would be: making the scoring depend on the activity, or exposing the thresholds as arguments; adding `list` and `delete` tools for saved trips, since today they can only be read through the `trips://saved` resource; caching forecasts to avoid repeated API calls; and moving storage from a JSON file to SQLite so it is safe when two writers run at the same time.
